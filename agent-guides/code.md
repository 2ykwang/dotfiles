# 코드 작성

## 1. 코딩 전에 생각하기

**가정, 불확실성, 트레이드오프를 드러낸다.**

- 작업 경로의 명시 지침을 읽고, 같은 종류의 기존 구현 몇 개와 대조한다.
- 명시 지침이 기존 구현의 관례보다 우선한다. 기존 코드가 있다는 것만으로 규칙이라 단정하지 않는다.
- 기술별 세부 규칙은 해당 레포의 정본에서 확인한다.
- 더 단순한 접근이 있으면 말한다. 근거가 있으면 반론한다.

## 2. 단순함 우선

**문제를 푸는 최소한의 코드만 쓴다. 추측성 코드는 쓰지 않는다.**

- 요청받지 않은 기능, 유연성, 설정 가능성을 넣지 않는다.
- 기존 컴포넌트, 훅, 유틸 중 책임과 입출력 계약이 맞는 것을 재사용한다.
- 실제로 같은 동작만 추출한다. 겉보기 유사성이나 사용처 수만으로 추상화하지 않는다.
- 서비스별 정책이 다르거나 갈라질 수 있으면 분리해 둔다.
- 함수와 파일은 책임, 복잡도, 읽기 비용으로 나눈다. 한 곳에서 쓰는 단순한 분기는 분리하지 않는다.
- 발생할 수 없는 시나리오의 에러 처리를 넣지 않는다.
- 줄 수보다 의도와 흐름이 명확한 쪽을 고른다.
- 시니어 엔지니어가 과도하다고 할 코드면 단순화한다.

## 3. 외과적 수정

**필요한 부분만 건드린다.**

- 주변 코드, 주석, 포매팅을 개선하지 않는다.
- 안 망가진 것을 리팩터링하지 않는다.
- 내 스타일과 달라도 기존 코드 스타일에 맞춘다.
- 관련 없는 죽은 코드는 언급만 하고 지우지 않는다.
- 설명이 모호하다는 지적에는 의도와 제약을 명료화한다. 동작이나 인터페이스 변경은 별도로 판단한다.

## 4. 목표 중심 실행

**성공 기준을 정하고, 검증될 때까지 반복한다.**

| 요청      | 검증 가능한 목표                         |
| --------- | ---------------------------------------- |
| 검증 추가 | 잘못된 입력의 테스트를 쓰고 통과시킨다   |
| 버그 수정 | 재현 테스트를 쓰고 통과시킨다            |
| 리팩터링  | 변경 전후로 테스트가 통과하는지 확인한다 |

- 다단계 작업은 `단계 → 검증 방법` 형식의 짧은 계획을 먼저 밝힌다.
- 변경 후 diff를 기존 패턴과 대조해 필요한 차이와 우발적인 스타일 차이를 구분한다.
- 기준이 모호하면 관련 자료로 구체화하고, 사용자 결정이 필요한 부분만 질문한다.
