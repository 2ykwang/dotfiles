# 코드 작성

AI Agent가 코드 작업에서 참고하는 코드 지침이다.

## 1. 코딩 전에 생각하기

**중요한 가정과 불확실성을 숨기지 말고, 트레이드오프를 드러낸다.**

구현 전:

- 작업 경로의 명시 지침과 같은 종류의 기존 구현을 소수 대조한다. 구조, 명명, 데이터 변환과 오류 처리 등 해당 변경의 패턴을 확인하되, 기존 코드의 존재만으로 필수 규칙이라고 단정하지 않는다.
- 명시적인 지침을 과거 구현의 관례보다 우선하고, 기술별 세부 규칙은 해당 레포의 정본에서 확인한다.
- 더 단순한 접근이 있으면 말한다. 근거가 있으면 반론한다.

## 2. 단순함 우선

**문제를 해결하는 최소한의 코드. 추측성 코드 금지.**

- 요청받지 않은 기능을 추가하지 않는다.
- 기존 컴포넌트, 훅, 유틸을 먼저 확인하고 책임과 입출력 계약이 맞는 구현을 재사용한다.
- 사용처 수나 겉보기 유사성만으로 과도하게 추상화하지 않는다. 실제로 같은 동작은 적절히 추출하고, 서비스별 정책 차이와 발산 가능성이 있으면 분리를 유지한다.
- 함수와 파일은 책임, 복잡도와 읽기 비용을 기준으로 나눈다. 한 곳에서 쓰는 단순한 분기까지 일률적으로 분리하지 않는다.
- 요청되지 않은 "유연성"이나 "설정 가능성"을 넣지 않는다.
- 발생 불가능한 시나리오에 대한 에러 처리를 하지 않는다.
- 줄 수를 줄이는 것보다 의도와 흐름이 명확한 구현을 선택한다.

자문: "시니어 엔지니어가 보면 과도하다고 할까?" 그렇다면 단순화한다.

## 3. 외과적 수정

**필요한 부분만 건드린다.**

기존 코드 수정 시:

- 옆에 있는 코드, 주석, 포매팅을 "개선"하지 않는다.
- 안 망가진 것을 리팩터링하지 않는다.
- 내 스타일과 달라도 기존 코드 스타일에 맞춘다.
- 관련 없는 죽은 코드를 발견하면 언급만 하고 삭제하지 않는다.
- 설명이 모호하다는 지적에는 의도와 제약을 명료화하고, 동작이나 인터페이스를 바꿀 필요가 있는지 별도로 판단한다.

## 4. 목표 중심 실행

**성공 기준을 정의하고, 검증될 때까지 반복한다.**

작업을 검증 가능한 목표로 변환:

- "검증 추가" → "잘못된 입력에 대한 테스트를 작성하고, 통과시킨다"
- "버그 수정" → "재현하는 테스트를 작성하고, 통과시킨다"
- "X 리팩터링" → "변경 전후로 테스트가 통과하는지 확인한다"

다단계 작업은 간결한 계획을 밝힌다:

```
1. [단계] → 검증: [확인 방법]
2. [단계] → 검증: [확인 방법]
3. [단계] → 검증: [확인 방법]
```

변경 후 diff를 기존 패턴과 대조하고, 필요한 차이와 우발적인 스타일 차이를 구분한다.
명확한 성공 기준이 있으면 독립적으로 반복할 수 있다. 기준이 모호하면 먼저 관련 자료로 구체화하고, 사용자 결정이 필요한 부분만 공통 사용자 지침의 질문 기준에 따라 확인한다.
